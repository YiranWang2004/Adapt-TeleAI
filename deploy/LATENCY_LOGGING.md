# 真机控制链路时序日志

版本：`20261015-feedback-refresh-6`。仍使用原来的三个终端指令，终端3带原有 `--output "deploy/recordings/real_日期_时间"` 即可。退出旧进程后重新启动才能加载更新。本次没有运行机器人控制。

自动振荡停控关闭，启动不查询/释放ai模式。START/A/UP/DOWN、PD数值、策略更新周期20ms、DDS写入周期2ms保持不变；SELECT/B/X及原有数据过期、关节范围、速度硬上限和倾角保护保留。

## 自动保存的文件

```text
real_日期_时间/
├── trace.jsonl                 # 每个控制周期，含latency关联字段
├── command_writes/
│   ├── schema.json             # 时钟、单位、关节顺序与字段说明
│   └── commands_*.npy         # 每次实际DDS Write尝试，通常约500Hz
├── lowstate/
│   ├── schema.json             # schema_version=2
│   └── lowstate_*.npy         # 默认200Hz，含命令/写入编号
├── mocap_packets.jsonl
├── summary.json               # 配置、版本、日志写入/丢弃/错误计数
├── summary.fault.json          # 异常退出时保存
└── latency_summary.json        # IO关闭并刷新日志后自动生成
```

`latency_summary.json` 在停止控制、关闭DDS和日志写入器后计算，不在运行中的控制循环里分析。异常退出仍会尝试生成。若分析失败，原始数据保留，`summary.json.latency_analysis.error` 保存原因，不覆盖原来的异常。直接强制杀死进程/断电可能来不及生成汇总，原始已落盘数据仍可事后分析。

## 关联与采样

- `command_id`：控制进程生成命令时分配。被500Hz重复写入的同一条命令保持相同ID。
- `control_cycle`：对应50Hz trace的cycle_index，用于确定POSITIONING、AMP、TO_POLICY、等待、挥拍、恢复等阶段。
- `feedback_sequence`：SDK每次回调递增，与raw反馈中的callback_sequence对应。200Hz原始采样会跳过部分回调编号，这是主动降采样，不等于网络丢包。
- `write_sequence`：每次Write递增，能区分“策略更新”和“重复保持旧目标”。阻尼停止命令也保存实际q/kp/kd和halted标记。
- `source_tick`：策略所用反馈的原始设备计数。`writer_source_tick`和writer_feedback_callback_time另记写入时可用的最新反馈。两者不是同一含义。
- 原始反馈保存最近已完成写入的command_id/write_sequence及写入开始/结束时间；“最近写过”不是“机器人正在执行”的确认。

`trace.latency` 保存反馈读取开始/结束、反馈跨进程包入队/出队、命令生成和入队完成时间、入队是否成功，以及反馈是否重复使用。SDK侧还统计完整回调序列的间隔最大值及发生时间、设备tick重复和回退提示。跨进程反馈队列主动保留较新状态，包序号缺口不能直接解释成设备网络丢包。

## 每条命令可以检查的时间段

| 时间段 | 用途 |
| --- | --- |
| 主机SDK回调 → 反馈包入队 | 回调后等待和子进程处理 |
| 反馈包入队 → 控制进程出队 | IPC队列与调度等待 |
| 控制进程使用反馈 → 命令生成 | FK、策略、过渡和控制处理 |
| 命令生成 → IO接受 | 命令队列和进程调度 |
| IO出队 → IO接受，以及IO接受 → 首次Write | 写入线程等待、准备和CRC |
| Write开始 → 返回 | SDK Write调用耗时 |
| 所用反馈SDK回调 → 对应命令首次Write | 按ID关联的主机闭环段，不再靠相邻trace猜配 |
| 连续Write间隔、计划与实际启动时间 | 检查500Hz线程抖动、长间断及旧目标保持 |

汇总按阶段给出中位数、P95、P99、最大值、有效数量和无效/负值数量；同时列出trace生成但未观察到首次Write的命令ID。缺失可能来自命令替换、队列提交失败或日志丢弃，需要结合对应计数判断，不能直接等同于网络丢包。

## 电机响应分析的边界

高频数据保留q、dq、tau_est、IMU、驱动状态、电压、温度；命令日志保留实际写出的q_target、kp、kd。串联后可核对目标变化与估计力矩、关节运动之间的相位关系。

所有主机时间使用同一台主机的time.monotonic，跨本地进程可比较。设备source_tick未经时钟同步；不能直接与主机秒数相减。新增日志仍不包含设备采样前的滤波时延，也没有驱动接收/执行确认时间。Write返回成功不证明实际执行，tau_est也不是独立力矩传感器。

事后可附加生成腰部0–40ms候选滞后的力矩相关曲线：

```zsh
cd /home/lxz/deploy_g1_pingpong
.venv/bin/python -m deploy.tools.analyze_latency \
  deploy/recordings/real_日期_时间 --response
```

该曲线保留所有候选值，不自动宣布“硬件延迟=Xms”。闭环中的周期振荡、传感器滤波和负载会造成相关峰多解，不能只取最高峰认定抖动原因。默认自动汇总只分析主机时序，不计算这项可选曲线。

## 日志开销和质量

写盘仍在有界后台队列中，控制回调不等待磁盘；记录复制、计时和IPC仍有CPU开销。约500Hz命令日志加200Hz原始反馈，10分钟二进制数据约250MB，另加trace和动捕包。每次记录使用独立输出目录，避免新旧schema或实验混在一起。

设置位于real.yaml：`record_io_diagnostics=true`、`record_command_writes=true`、`record_lowstate_hz=200`、`latency_auto_summary=true`。schema和summary记录写入、丢弃和错误计数。应以新日志中的这些计数检查数据完整性，而不能假设所有生成命令都写出或所有采样都落盘。

本版验证包括合成跨进程命令关联、停止时实际阻尼目标记录、设备tick回绕/回退、已知合成8ms滞后曲线、完整回归，以及无真实SDK通道的写入日志开销测试。开销测试保留真实模型推理和HG CRC，发布器/订阅器都是stub，不是机器人链路测试。

本地与.200完整回归各98项通过。.200独立开销测试每组8秒：关闭/开启命令日志时，控制处理耗时中位数为0.802/0.775ms，P95为1.952/1.331ms；样本短且运行顺序固定，不能据此声称零开销。开启时4004条Write记录及1611条原始反馈全部落盘，日志队列丢弃为0。两组仍分别出现约61/53ms的最大写入间隔；开启组400个生成命令中398个观察到首次Write，另2个被跳过。它们是stub链路中的调度/命令保持现象，不能视为真实机器人网络时延，也说明日志落盘完整不代表每条生成命令都被写出。下一次真机应重点检查这些间断是否在TO_POLICY或抖动开始时出现。

## 2026-10-15 两次真机复查后的反馈读取修正

旧版控制进程在跨进程队列瞬时为空时会直接复用上一周期反馈，新增日志证实部分周期因此使用约21ms旧状态，尽管SDK已有新反馈。新版第一次读取最多等待一个IO轮询间隔（当前1ms），随后只做非阻塞排空；数据过期保护保留。它减少无谓的整周期复用，并不能消除系统调度暂停，也不是已验证的真机抖动根治措施。相关回归新增两项，本地和.200各100项通过。详见 `SHAKING_REVIEW_20261015.md`。
